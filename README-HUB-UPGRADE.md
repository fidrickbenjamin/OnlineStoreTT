# Tactical Trends Marketplace — Food, Ride & Delivery Hubs

This is a working, incremental source-code upgrade for the latest marketplace project. Apply it after the previous account, seasonal, unpaid-order/splash and top-header updates. It adds three hubs, partner/driver applications, quotations, dispatch, foreground GPS sharing and a reconciled driver earnings/payout workflow.

## Install

1. Back up your current source and database.
2. Copy the ZIP’s `backend`, `frontend` and optional `tests` folders into the project root, preserving paths and replacing matching files. Keep the included shared files together. Do not replace the whole project with this incremental ZIP.
3. No new npm dependencies or database migration commands are required. The new models create their own hub collections/indexes in your existing MongoDB database. Existing store orders/products remain separate.
4. Build and redeploy both backend and frontend. From the project root, the existing Render build command is:

   `npm ci --legacy-peer-deps && npm ci --prefix frontend --legacy-peer-deps && npm run build --prefix frontend`

   Start command remains `npm start`.

   For local frontend compilation: `npm run build --prefix frontend`.
5. Sign in as your existing admin and open `/admin/hubs` (Hub Operations in the admin menu).
6. Set your actual rates and food commission, approve businesses/drivers, and test the complete workflow before inviting customers. The default base/per-kilometre values are starter configuration, not researched taxi tariffs.

The backend routes are mounted through the existing order router. `backend/app.js` and its CORS setup are not included or edited. The ZIP also excludes every env/config.env file, all build folders, node_modules, git data and PaymentMethod.jsx.

The updated Header.jsx is based on the latest delivered top-header version. This ZIP expects its Header.css and SeasonalContext.jsx dependencies from that earlier update to already be installed. The previous top-header ZIP should be applied first if you have not applied it yet.

## What customers can use

- `/food-hub`: approved restaurants and bars, business icons/photos, category tags, community search and opening/acceptance status.
- `/food-hub/:id`: menu sections, dishes/drinks, optional extras, quantities, food subtotal, delivery/collection choice and order instructions. One business per food request.
- `/ride-hub`: pickup/destination details and optional map pins, passengers, requested time, road/community estimates and ride requests.
- `/delivery-hub`: pickup/drop-off, contact details, package/handling/payment instructions, requested time and delivery requests.
- `/me/activity`: hub activity list and request details, timeline, final quote acceptance, permitted cancellations, payment status, assigned driver details and completion PIN.
- Existing marketplace purchases remain under My Orders and use their existing checkout/payment flow.

Submitting a request does not charge the customer or reserve a driver. Admin confirms availability and issues the total, and the customer explicitly accepts it. A food subtotal is recalculated from the database; browser-supplied totals are ignored. Delivery/service fees are visible before acceptance. Quotes expire after 30 minutes unless accepted; accepted bookings keep their recorded amount.

Food menu prices and service rates should include any applicable taxes in the amounts you configure. The existing store’s separate 15% pricing logic is not automatically applied to the new services. Configure the new prices appropriately for your business arrangements.

## Business Centre

Any signed-in account can apply at `/business-centre`. Business applications start Pending even if a client tries to submit approval fields.

1. Submit business name/type/contact, optional public HTTPS photo/logo link, opening hours and pickup details.
2. Admin approves the application in Hub Operations. The owner then switches on “Accept food orders now”.
3. The owner adds menu items, categories, prices, optional extras and optional public HTTPS photo links. The default storefront icon is used when no image is supplied. This release uses image links rather than adding a new image-upload service.
4. The owner can mark dishes unavailable, edit menu items, change displayed hours and stop taking new orders when closed or busy. Displayed hours are informational; the acceptance switch controls ordering.
5. New orders appear in the business dashboard. The business accepts or declines them; accepted orders then receive an admin delivery/final quote.
6. After the customer confirms, the business marks the order ready. Mobanking orders require verified payment before collection readiness.
7. Food deliveries are dispatched from the same booking record, so duplicate delivery records cannot be generated by a retry. Customer collection orders have no delivery fee or driver payout.
8. The business can view its completed, paid proceeds and recorded settlement status. Admin records actual business settlements. Business payouts are manually reconciled, not automatic bank transfers.

Menu changes do not rewrite existing order snapshots. Contact admin to change application identity/pickup details beyond the owner’s operational controls in this release.

## Ride and delivery pricing / maps

### Without Google keys

The hubs still work: customers enter communities, landmarks and phones, and admin quotes the job. Admin may configure directional community-to-community rates. If neither a matching community rate nor road route exists, the UI explicitly says a manual quotation is required. It never substitutes straight-line distance or fabricates a fare.

### With Google Maps configured

Add these values directly in your deployment settings; no env file is provided in the ZIP:

- `HUB_MAPS_BROWSER_KEY`: a Google browser key for Maps JavaScript API. This key is intentionally delivered to the browser. Restrict its allowed website referrers to your production/approved testing domains and restrict it to the required API.
- `HUB_GOOGLE_ROUTES_KEY`: a separate server-side key for Routes API. It stays on the backend and is never returned by `/hubs/config`. Restrict it to the required API and follow Google’s server-key guidance.

Enable the relevant Google APIs and billing. Set request quotas and billing alerts in your Google project. Google usage is not guaranteed to be free. Restart/redeploy after setting the values.

The map allows pickup/destination pin selection and “Use my location” with permission. Location/coordinates must fall within the configured Dominica bounding range. Landmarks and operator review remain important; the bounding range is not detailed island/road geofencing.

“Calculate estimate” asks the backend for a road route. The server computes price from your base and per-road-kilometre settings. A matching directional community rate takes precedence. Road duration is an estimate, not a promise or live traffic ETA. Driver pay is separately agreed in the admin quote.

The request map can draw the returned road polyline. Active job maps display pickup/destination pins and the assigned driver’s latest reported position. Open-in-Maps links are available when coordinates exist. This release does not continuously recalculate a traffic-based arrival time.

Official setup references:
- https://developers.google.com/maps/documentation/javascript/get-api-key
- https://developers.google.com/maps/documentation/routes/get-api-key
- https://developers.google.com/maps/documentation/routes/compute_route_directions

Live credentials/provider billing were not available in this work session. API request/response handling and the map adapter were tested using local provider fixtures, not charged live routes.

## Driver Centre and dispatch

Drivers apply at `/driver-centre`, entering contact details, vehicle/capacity, registration, licence reference, communities and delivery/taxi services. This release records references; admin checks supporting documents separately before checking the verification box and approving suitability. Approval is not automated document verification.

Approved drivers switch themselves available. Admin offers a confirmed booking to a suitable available driver. Drivers see the route communities and agreed earnings before accepting, and may decline. Exact customer addresses/contacts are revealed after acceptance. Drivers cannot accept a job offered to someone else or fulfil their own customer booking. One driver can hold one active job at a time.

Admin can release an assigned driver before pickup, with a reason, then offer the job to someone else. In-progress pickups require operator resolution rather than automatic reassignment.

The driver confirms collection/passenger pickup, then completes using the customer’s six-digit PIN. Only the customer/admin can read that PIN. Admin can record an exception after entering a review reason. A paid cancellation requires refund review, and actual refunds are recorded with their reference; no payment is automatically refunded by this release.

## Foreground GPS tracking

On an assigned or picked-up job the driver can choose “Share location for this job”. It uses actual browser geolocation with permission and sends updates approximately every five seconds when readings are available. Sharing stops on page unmount or when the driver turns it off. Only the assigned approved driver can submit positions for that active job.

Customers refresh job status/location through polling. The last update time and accuracy are shown; a position older than two minutes is labelled stale and is not displayed as a fresh driver marker.

Keep the driver page open. Browser backgrounding, locked phones, poor signal, denied permissions and sleeping infrastructure can interrupt updates. Reliable phone-locked/background tracking requires a later native driver-app project. This ZIP does not claim to implement that.

## Payment, earnings and payouts

New hubs support:
- CASH, with admin payment verification and driver cash reconciliation.
- NBD/Mobanking, with customer receipt image/reference and admin review. PNG/JPEG/WebP receipts are private and limited to 450 KB; image signatures are validated. Rejected receipts require another submission before they can be verified. Mobanking jobs cannot reach pickup before verified payment.

These hub flows do not use PayPal/ShopDM automatic checkout yet. Your existing store PayPal/ShopDM/Card code and PaymentMethod.jsx are untouched. Hub payout controls record manual transfers; they do not debit a bank or send a PayPal payout.

All money is stored in integer cents. The quote records driver pay separately from the service fee. Food commission is snapshotted from the configured percentage, and business proceeds are food subtotal less that commission.

Driver earnings become withdrawable only after completion and verified payment. When cash was held by a driver, admin must reconcile that cash first. “Confirm driver cash settled” means the driver has remitted the full customer amount to the appropriate store/business settlement process, and their agreed driver pay will then be paid through the wallet. Do not let a driver retain their pay and then pay the same amount again from this wallet.

The wallet distinguishes:
- Total earnings credited/released.
- Available amount that can be requested.
- Reserved amount for pending payout requests.
- Completed jobs still awaiting payment/cash verification.
- Payout history with Requested, Paid or Rejected status and references.

Minimum payout request is XCD 1.00. A request atomically reserves the requested amount. Admin transfers the money using the agreed method and then records its actual reference as Paid, or rejects with a reason and releases the reserved balance. Duplicate requests/reviews cannot spend/release the same balance twice. Each job can credit its driver only once.

An internal earnings ledger is not a bank balance or an automatic money-transfer service. Reconcile real receipts, business proceeds, cash and transfers before recording them.

## Admin, notifications and operation

`/admin/hubs` provides the dispatch board, application reviews, payout reviews and configurable fare/commission settings. Job details hold quotation, offer, receipt, cash, merchant settlement, cancellation and refund controls. Conflicting edits are rejected using revisions, rather than silently overwriting newer changes.

New requests/jobs persist in the database and appear on admin/partner/driver dashboards. Dashboards poll approximately every 15 seconds, show in-app update alerts, and can request browser notification permission while the dashboard is open. Job details refresh approximately every 10 seconds.

This release does not replace Mailtrap, send new hub notification emails/SMS or deliver closed-browser push alerts. Your previous Google-mail migration remains a separate task. Keep the dispatch dashboard open during operation. Reliable operational dispatch should use an always-on deployment; a sleeping Render free instance cannot guarantee timely offers, tracking or alerts.

Use a small supervised launch first. Check route coverage, fare rules, cash procedures, business opening controls, driver verification and actual payout accounting. No real restaurants/drivers/menu items or fabricated paid jobs are seeded by this ZIP. Public lists will be empty until you onboard approved partners.

Lists currently display recent records: up to 200 customer/business/driver jobs and up to 300 admin jobs. Older records are retained and their detail URLs still work. Bulk history exports, advanced pagination, merchant-requested payouts, multi-restaurant baskets, automatic matching, automatic transfers, continuous traffic ETA and native background tracking are future extensions.

Per-instance burst limits protect routing requests, new requests, completion attempts and GPS updates. They are not a substitute for provider-side quotas, production monitoring and dispatch staffing.

On sign-in/registration the shared API cache is reset, helping prevent one account’s partner/driver data from being displayed after an account switch.
